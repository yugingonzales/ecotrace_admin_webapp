## System Overview

The EcoTrace Admin Portal is a React-based web application for managing tree monitoring operations, events, submissions, and push notifications to mobile app users. It provides a full CRUD interface backed by a Node.js/Express API with MariaDB.

### 3. Alert Management ✅ **[Updated - 2026-11-02]**
Complete push notification system with mobile app integration.

**Features:**
- Create, read, update, delete alerts
- 7 notification codes stored for client-side routing
- Event-linked alerts (upcoming_event, event_live, event_conclusion, event_extended, event_update)
- Platform-wide announcements
- Verification status updates
- Character counters (160 for title, 5000 for body)
- Status badges (published/draft)
- Read/unread tracking per user
- Alert-event associations

**Notification Codes:**
1. `platform_announcement` - General announcements (all users)
2. `upcoming_event` - New event published (all users)
3. `event_live` - Event started, geofencing active (all users)
4. `event_conclusion` - Event ended (participants only)
5. `event_extended` - Deadline extended (participants only) ⭐ NEW
6. `event_update` - Event details changed (participants only)
7. `verification_update` - Submission reviewed (specific user)

**Delivery and routing status:**
- `event_live` and `event_conclusion` are generated by `processEventLifecycle()` every 60 seconds for due active events.
- `event_extended` is generated synchronously when an admin extends `end_date` through `PATCH /api/events/:id`.
- Event alerts include `event_id`; conclusion, extension, and update alerts target joined participants, while live alerts target active non-admin users.
- The API stores alerts and recipient read state; it does not provide OS-level push delivery by itself. The mobile app retrieves the feed when it loads or refreshes alerts.
- Mobile event-live routing is implemented. Announcement and event-extension tap routing remain open mobile integration work.

**API Endpoints:**
- `GET /api/alerts` - List alerts (authenticated, shows user's read status)
- `POST /api/alerts` - Create alert (admin/staff only)
- `PATCH /api/alerts/:id` - Update alert (admin/staff only)
- `DELETE /api/alerts/:id` - Delete alert (admin only)
- `PATCH /api/alerts/:id/read` - Mark alert as read (authenticated)
- `POST /api/alerts/:id/read` - Mark alert as read (authenticated, legacy)

**Files:**

## Known Issues & Limitations

### Current Limitations
1. **Write operations:** Most non-event admin actions persist to `localStorage`, not MariaDB (by design for gradual rollout)
2. **Backend tests:** No dedicated backend test files currently written (smoke tested manually)
3. **File uploads:** Photo evidence storage not yet implemented
4. **OS push delivery:** Alerts are persisted and exposed through the API; a push provider/FCM delivery worker is not implemented
5. **Mobile announcement routing:** `platform_announcement` alerts are displayed in the alert feed, but tapping them does not yet open the announcements sheet
6. **Mobile extension routing:** `event_extended` is generated by the API but is not yet included in the Flutter actionable event-code switch

### Technical Debt
- Dead code in `src/lib/api.js` (12 of 15 functions unwired)
- Three overlapping styling systems (CSS, Tailwind, inline styles)
- No auth on backend routes (prototype-grade, deferred by user)
